### [2026-07-27 20:45] Fixed

**Tech:** `AndrecordApplication.kt` — removed `whisperAsrEngine` from `AppContainer`; `TranscriptionWorker.kt` — constructs `SherpaOnnxWhisperAsrEngine(applicationContext)` as a local instance inside `doWork()` instead, released in the same `finally`; `enqueue()` switched from a plain `WorkManager.enqueue()` to `enqueueUniqueWork(UNIQUE_WORK_NAME, ExistingWorkPolicy.APPEND_OR_REPLACE, request)`  
**Dev:** The previous fix's `release()` call introduced a real race: `SherpaOnnxWhisperAsrEngine` was a process-wide singleton shared by every `TranscriptionWorker` run, but nothing prevented two runs (e.g. two recordings finishing close together, or retrying two failed sessions) from executing concurrently against it — one run's `finally` could release the native recognizer while another was still mid-decode (a native use-after-free), or both could race into allocating their own duplicate ~362MB recognizer with only one ever released. Fixed by not sharing the engine at all: each `TranscriptionWorker` run now owns its own instance end-to-end, eliminating the race by construction rather than by adding synchronization to a shared object. Also serialized all transcription work via `enqueueUniqueWork`/`APPEND_OR_REPLACE` (verified against the real WorkManager 2.9.1 bytecode that this genuinely blocks concurrent execution, not just orders it) so two ~362MB native model loads can never happen at once regardless — `_OR_REPLACE` specifically avoids a permanently-failed run blocking every future transcription forever, which plain `APPEND` would not have.  
**Plain:** Fixed a rare but real crash risk where finishing two recordings close together (or retrying two failed ones) could corrupt the transcription engine's memory; transcriptions now always run one at a time.  
**Why:** The previous fix (holding less memory over time) accidentally introduced a new way for that same memory to be used unsafely if two recordings needed processing around the same time — this closes that gap before the feature's first real use.

### [2026-07-27 20:30] Fixed

**Tech:** `app/src/main/assets/models/asr_offline/small.en-{encoder,decoder}.onnx` swapped fp32 → int8; `app/build.gradle.kts` — `androidResources.noCompress += listOf("onnx")`; `TranscriptionWorker.kt` — `check(transcriptSegments.isNotEmpty())` replaced with a `realSegmentCount > 0` check that ignores `FAILURE_PLACEHOLDER` text, plus `Log.w` on both previously-silent `catch` sites and a `finally { whisperAsrEngine.release() }`; `WhisperChunker.kt` — sub-split chunks now overlap by `PADDING_MS` instead of butt-joining, and the midpoint clamp is coerced so it can only shrink padding, never truncate a segment's own span; `OfflineAsrEngine.release()` added and implemented in `SherpaOnnxWhisperAsrEngine` via a nullable `recognizer` instead of `by lazy`; `notifyFailed()`'s notification channel renamed from "Transcript ready" to "Transcript processing failed"
**Dev:** Final whole-branch review of the offline-refinement feature turned up nine findings, fixed in one pass. Biggest one: the app was bundling full-precision Whisper-small.en (~968MB) with no `noCompress` exemption, meaning the OS had to fully decompress ~968MB into RAM before ONNX could read it — untested on a real device and a real OOM risk. Switched to int8-quantized weights (~374MB combined, well under 1% accuracy loss vs fp32 in practice) and added `noCompress` for `.onnx` assets so the OS never has to decompress model weights into RAM at all — a real, measured ~130MB *increase* in APK size (int8 weights compress meaningfully, 30-37%) traded deliberately for materially safer peak load-time memory; debug APK went from ~967MB to ~701MB even with that trade. Also closed two silent-failure paths in `TranscriptionWorker` (zero diarization segments, and Whisper "succeeding" while returning blank text for every chunk) that could previously finalize a session to `READY` with no transcript, wiping out anything `RecordingService` had already flushed; both now correctly throw into the existing retry → `markProcessingFailed()` path. Released the Whisper recognizer's native memory (~362MB int8) after each `TranscriptionWorker` run instead of holding it for the app's entire process lifetime. Removed the now-dead `successCount` variable that the old check depended on. Added/updated unit tests for all of the above (`WhisperChunkerTest`, `TranscriptionWorkerLogicTest`).
**Plain:** The offline transcript-refinement feature is now far less likely to crash or freeze from running out of memory on a real phone, transcription failures now show up as a clear "processing failed, tap to retry" instead of silently leaving a session with an empty or half-missing transcript, and a long uninterrupted speaker's transcript should no longer have words corrupted at chunk boundaries.
**Why:** This feature had never run on a real device and several of its safety nets had gaps that would only bite in real-world conditions (a genuinely long monologue, overlapping speakers, a device under memory pressure) — this pass closes those gaps before it gets its first real on-device test.

### [2026-07-27 19:40] Changed

### [2026-07-27 17:35] Fixed

**Tech:** `RecordingController.activeSessionId` — marked `@Volatile`  
**Dev:** The 17:05 fix gave `activeSessionId` its first reader (`reportRecordingEnded(sessionId)`), but the field itself was still a plain `private var`. It's written from Main (`toggle()`/`start()`/`stop()`) and read from `Dispatchers.Default` (the notification-Stop teardown coroutine in `RecordingService`), with no other synchronization between those threads -- so without `@Volatile`, the JMM permitted the teardown coroutine to observe a stale value and let the exact race the 17:05 fix was meant to close through anyway. Every analogous cross-thread field in `RecordingService.kt` (`sessionId`, `wavFile`, `failedSessionId`, `stopRequested`, `stopping`) is already annotated for this same reason; this field was the odd one out until now. Verified via `RecordingControllerTest` (9 tests, all passing) -- reference assignment is atomic so there's no torn-read risk, only the staleness `@Volatile` fixes.  
**Plain:** Internal correctness fix -- no user-visible behavior change, but makes the previous fix actually reliable on real hardware rather than just correct in theory.  
**Why:** A guard that's logically correct but not properly synchronized across threads can still fail silently on a real device even though it looks right in code and passes single-threaded tests -- this closes that gap.

### [2026-07-27 17:25] Fixed

**Tech:** `RecordingScreen` — auto-scroll `LaunchedEffect` switched from `animateScrollToItem()` to `scrollToItem()`  
**Dev:** Partial-transcript updates arrive roughly every 80-130ms during continuous speech, which is faster than a scroll animation typically takes to settle, so the animated scroll added in the 16:55 fix was continually restarted mid-flight and never actually finished -- visible jitter with no benefit over an instant jump. `scrollToItem()` performs the same "jump to `lastIndex`" without animating, which is strictly more robust for a feed that updates faster than a typical scroll-animation duration. Not unit tested, same as the original auto-scroll change: pure Compose scroll behavior with no Compose UI test harness set up in this project.  
**Plain:** The live transcript's auto-scroll now jumps straight to the newest line instead of visibly stuttering while it tries (and fails) to animate there.  
**Why:** The animated auto-scroll added earlier looked janky during continuous speech because new lines kept arriving before the animation finished -- an instant scroll fixes that without giving anything up.

Replaced with the standard local-font-resource mechanism instead: three Regular-weight OFL-licensed `.ttf` files (Space Grotesk, Source Serif 4, IBM Plex Mono — all confirmed as `SIL Open Font License, Version 1.1` via each font's `OFL.txt`) downloaded directly from Google's `google/fonts` GitHub repo and placed under `res/font/`, referenced via plain `Font(R.font.xxx)` with no provider and no certs involved at all. Confirmed `ui-text-google-fonts` was never added to `app/build.gradle.kts`. Verified the three `.ttf` files are present inside the assembled APK (`res/font/*.ttf`) via `unzip -l`.
**Plain:** The app's visual style (a display font for headings, a serif for body text, a monospace for labels) now ships as font files bundled directly inside the app, instead of trying to download them from Google's servers the first time they're needed.
**Why:** Wanted the distinctive typography from the design spec without compromising the app's core privacy promise of truly never touching the network, and without needing to guess at security-sensitive certificate bytes that could silently fail.
